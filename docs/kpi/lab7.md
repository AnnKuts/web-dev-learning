# Звіт про виконання практичної роботи №7

**Варіант №3**

Для вимірювань використано Laravel-застосунок [`project8-9/blog/`](../../project8-9/blog/) та окрему локальну SQLite-базу `/tmp/lab7-blog.sqlite` зі 100 тестовими статтями одного автора. У цьому проєкті списку статей (`resource=articles` у формулюванні завдання) відповідає захищений Laravel Sanctum ендпоінт `GET /api/posts`.

Усі вимірювання проводилися локально; production-база Railway для тестів не використовувалася. Наявний `.env` для цих вимірювань не змінювали: тестові параметри передавалися під час запуску процесу.

## Крок 1. Виміряти базовий час виконання «як є»

> Обгорніть виклик вашого спискового API-ендпоінта (`api.php?resource=...`) з практикуму №6 викликами `microtime(true)` і `memory_get_peak_usage(true)` до і після; запишіть отримані значення — це ваша базова лінія («до»).

Для вимірювання часу та пам'яті використано middleware [`ProfilePostListing.php`](../../project8-9/blog/app/Http/Middleware/ProfilePostListing.php). Він заміряє час обробки `GET /api/posts` через `microtime(true)`, фіксує пікове використання пам'яті через `memory_get_peak_usage(true)` та записує результати в Laravel log, не змінюючи JSON-відповідь.

До додавання індексу отримано такі показники:

- Час обробки запиту — 33.858 мс
- Пікове використання пам'яті — 10 485 760 байтів
- HTTP-статус - 200

Пікова пам'ять фіксується після обробки запиту. Оскільки замір виконано для одного запиту без контролю прогріву PHP-процесу, цей результат використовується як орієнтир.

## Крок 2. Провести навантажувальне тестування «як є»

> Запустіть `ab -n 200 -c 20` на цей самий ендпоінт; зафіксуйте `Requests per second`, `Time per request (mean)` і `Failed requests` — це також частина базової лінії.

Для базового тесту індекс було прибрано лише з локальної тестової бази, ApacheBench запускався командою:

```bash
ab -n 200 -c 20 http://127.0.0.1:8797/api/posts
```

Отримані результати:

| Показник | До оптимізації |
|---|---:|
| Complete requests | 200 |
| Failed requests | 0 |
| Requests per second | 174.91 |
| Time per request (mean) | 114.347 мс |
| Розмір JSON-відповіді | 11 157 байтів |

Для доступу до захищеного маршруту використовувався локальний режим `DEV_AUTH_BYPASS=true` з попередньо створеним тестовим користувачем. Усі відповіді в цьому запуску мали HTTP-статус `200`.

## Крок 3. Знайти вузьке місце та порахувати SQL-запити

> Додайте лічильник викликів `query()/execute()` (наприклад, статичну змінну або обгортку над PDO) і виведіть, скільки SQL-запитів виконується на один виклик вашого ендпоінта; для сценарію вашого варіанта це має показати проблему N+1.

У [`ProfilePostListing.php`](../../project8-9/blog/app/Http/Middleware/ProfilePostListing.php) для підрахунку SQL-запитів використано `DB::listen()`. Під час завантаження сторінки з 15 статтями зафіксовано 4 SQL-запити: підрахунок записів для пагінації, завантаження статей, авторів і тегів.

У [`PostController.php`](../../project8-9/blog/app/Http/Controllers/PostController.php) вже застосовано eager loading `with(['user', 'tags'])`, тому типової проблеми N+1 під час отримання списку статей немає.

Для демонстрації N+1 окремо створено [`lab7_scenarios.php`](../../project8-9/blog/scripts/lab7_scenarios.php). У ньому підрахунок статей автора виконується всередині циклу: для 15 статей це дає 15 SQL-запитів. Цей тестовий цикл не є частиною основного API.

Сценарій працює лише з тестовою SQLite-базою у тимчасовому каталозі, якщо задано `APP_ENV=local` або `testing`, `CACHE_STORE=array`, а `LAB7_BENCH_DB_PATH` збігається зі шляхом до бази. Якщо статей немає, виконання припиняється без створення нових записів.

## Крок 4. Додати індекс на стовпець фільтрації

> Виконайте `EXPLAIN` для запиту з фільтром вашого варіанта до створення індексу, створіть `CREATE INDEX ...` на потрібний стовпець, повторіть `EXPLAIN` і порівняйте результати до та після.

У таблиці `posts` автор статті визначається полем `user_id`. Для перевірки використано запит:

```sql
SELECT * FROM posts WHERE user_id = 1;
```

Результати `EXPLAIN QUERY PLAN` у локальній SQLite:

| До створення індексу | Після створення індексу |
|---|---|
| `SCAN posts` | `SEARCH posts USING INDEX posts_user_id_lab7_idx (user_id=?)` |

До міграції `PRAGMA index_list('posts')` не показував індексів для цієї таблиці. Після додавання індексу SQLite почала використовувати пошук за `user_id` замість повного перегляду таблиці.

Індекс додається міграцією [`2026_11_10_000000_index_posts_user_id.php`](../../project8-9/blog/database/migrations/2026_11_10_000000_index_posts_user_id.php). Перед створенням вона перевіряє, чи вже існує індекс, першим стовпцем якого є `user_id`, щоб не створювати дубль. SQLite не повертає поля MySQL `type` та `rows`, тому для порівняння наведено фактичний вміст поля `detail`.

## Крок 5. Усунути N+1-запит

> Перепишіть сценарій вашого варіанта так, щоб замість запиту в циклі виконувався один запит (`GROUP BY`, `JOIN` або одне агрегатне `SELECT`); переконайтеся лічильником із кроку 3, що кількість запитів справді зменшилася.

У тестовому сценарії 15 окремих запитів на підрахунок статей автора:

```sql
SELECT COUNT(*)
FROM posts
WHERE user_id = ? AND deleted_at IS NULL;
```

замінено одним агрегатним запитом:

```sql
SELECT user_id, COUNT(*) AS cnt
FROM posts
WHERE deleted_at IS NULL AND user_id IN (1)
GROUP BY user_id;
```

Кількість SQL-запитів скоротилася з 15 до 1 а результат підрахунку для автора залишився правильним — 100 статей.

Час виконання окремого сценарію:

| Умови | 15 запитів у циклі | Один запит із `GROUP BY` |
|---|---:|---:|
| До додавання індексу | 0.747 мс | 0.629 мс |
| Після додавання індексу | 1.222 мс | 0.410 мс |

Ці вимірювання стосуються окремого SQL-сценарію, а не навантажувального тесту HTTP-ендпоінта.

## Крок 6. Додати кешування «важкого» запиту

> Реалізуйте файловий кеш або APCu для агрегатного чи спискового запиту з TTL 30–60 секунд. Переконайтеся, що після зміни даних кеш інвалідується або застаріває за TTL.

У [`PostService.php`](../../project8-9/blog/app/Services/PostService.php) метод `listRecent($limit)` кешує список останніх статей на **45 секунд** через Laravel Cache. Для нього додано захищений маршрут `GET /api/posts/recent?limit=10` у [`routes/api.php`](../../project8-9/blog/routes/api.php). Відповідь містить статті разом з авторами й тегами.

Після створення, редагування або видалення статті, якщо транзакцію успішно завершено, збільшується версія ключа кешу. Наступний запит отримує оновлені дані, а старі записи видаляються після завершення TTL.

Результати перевірки кешування:

| Умови тесту | Холодний виклик | Повторний виклик |
|---|---:|---:|
| Файловий кеш, початковий вимір | 3 SQL-запити; 8.653 мс | 0 SQL-запитів; 0.581 мс |
| `CACHE_STORE=array`, окремий запуск | 3 SQL-запити; 9.107 мс | 0 SQL-запитів; 0.149 мс |

Ці два запуски виконувалися з різними драйверами кешу, тому їхні абсолютні значення часу між собою не порівнювалися. Тести також перевіряють інвалідацію після створення, редагування та видалення статті, а також відсутність інвалідації після відкату транзакції.

## Крок 7. Повторне вимірювання після оптимізації

> Виконайте той самий профайлінг і той самий `ab`-тест на оптимізованому коді; зафіксуйте нові значення часу, пам'яті та `Requests per second`.

Після додавання індексу повторно протестовано `GET /api/posts` на локальній SQLite-базі зі 100 тестовими статтями. Використано ту саму команду:

```bash
ab -n 200 -c 20 http://127.0.0.1:8797/api/posts
```

ApacheBench показав 153.97 запитів/с і середній час 129.897 мс. Усі 200 запитів завершилися. Розмір відповіді в цьому запуску становив 12 372 байти

В окремому попередньому записі профайлера для оптимізованого ендпоінта зафіксовано 2.529 мс, пікове використання пам'яті 2 097 152 байти та 4 SQL-запити.

За результатами нового навантажувального тесту пропускна здатність зменшилася зі 174.91 до 153.97 запитів/с, а середній час запиту зріс зі 114.347 до 129.897 мс. Отже, прискорення основного списку статей у цьому запуску не спостерігалося. Ендпоінт `/api/posts` уже використовує eager loading і не виконує підрахунок статей автора в циклі. Крім того, розмір відповіді відрізнявся між двома тестами, тому їхнє порівняння є орієнтовним.

## Крок 8. Порівняння результатів

> У README чи коментарі на початку скрипта зведіть у таблицю або список час виконання, кількість SQL-запитів і `Requests per second` до та після оптимізацій; додайте пояснення різниці.

| Показник | До оптимізації | Після оптимізації |
|---|---:|---:|
| Час обробки за профайлером, мс¹ | 33.858 | 2.529 |
| Пікова пам'ять за профайлером, байти¹ | 10 485 760 | 2 097 152 |
| SQL-запитів на `GET /api/posts` | 4 | 4 |
| Requests per second | 174.91 | 153.97 |
| Time per request (mean), мс | 114.347 | 129.897 |
| Failed requests | 0 | 0 |
| Розмір відповіді, байти | 11 157 | 12 372 |
| SQL-запитів для підрахунку статей автора² | 15 | 1 |

¹ Показники одного запиту отримано з окремих запусків без однакового контролю прогріву PHP-процесу.  
² Оптимізацію підрахунку перевірено в ізольованому сценарії, а не безпосередньо в `GET /api/posts`.

Найпомітнішу зміну отримано для підрахунку статей автора: замість 15 запитів виконується один запит із `GROUP BY`. Індекс на `posts.user_id` також дозволив SQLite використовувати індексний пошук замість повного сканування таблиці.

В основному `GET /api/posts` кількість SQL-запитів залишилася незмінною, а повторний навантажувальний тест показав дещо нижчу пропускну здатність. Оптимізація N+1 перевірялася окремо, а кешування реалізовано для `/api/posts/recent`, тому їх не можна вважати причиною прискорення чи сповільнення звичайного списку. На HTTP-результати могли вплинути умови локального запуску та різниця в розмірі відповіді.

Усі зміни до індексів та тестових даних для цього дослідження виконувалися в локальній базі. Production PostgreSQL не використовувалася для навантажувального тестування.
