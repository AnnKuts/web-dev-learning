# Звіт про виконання практичної роботи №7

Для вимірювань використано застосунок [`project8-9/blog/`](../../project8-9/blog/) і окрему локальну SQLite-базу `/tmp/lab7-blog.sqlite` зі 100 тестовими статтями одного автора. Railway та наявний `.env` не змінювалися. Варіант №3 — блог/CMS для статей: `resource=articles` у цьому Laravel-проєкті відповідає захищеному Sanctum маршруту `GET /api/posts`.

### Крок 1. Виміряти базовий час виконання «як є».

> Обгорніть виклик вашого спискового API-ендпоінта (api.php?resource=...) з практикуму №6 викликами microtime(true) і memory_get_peak_usage(true) до і після; запишіть отримані значення - це ваша базова лінія («до»).

Локальний middleware [`ProfilePostListing.php`](../../project8-9/blog/app/Http/Middleware/ProfilePostListing.php) вимірює `GET /api/posts` через `microtime(true)` та `memory_get_peak_usage(true)` і пише результат у Laravel log, не змінюючи JSON. Перед додаванням індексу зафіксовано `33.858 мс`, пікова пам'ять `10 485 760 байт`, статус `200`. Показник одного запиту залежить від прогріву процесу.

### Крок 2. Провести навантажувальне тестування «як є».

> Запустіть ab -n 200 -c 20 на цей самий ендпоінт; зафіксуйте Requests per second, Time per request (mean) і Failed requests - це також частина базової лінії.

Після вилучення індексу лише з локальної тестової БД виконано `ab -n 200 -c 20 'http://127.0.0.1:8797/api/posts'`: `174.91` запитів/с, `114.347 мс` на запит, `0` невдалих, `200` завершених. Локальний `DEV_AUTH_BYPASS=true` використав попередньо створеного тестового користувача; усі відповіді мали статус `200`, довжину JSON `11157` байтів. Це не тест Railway.

### Крок 3. Знайти вузьке місце - порахувати кількість SQL-запитів.

> Додайте лічильник викликів query()/execute() (наприклад, статичну змінну або обгортку над PDO) і виведіть, скільки SQL-запитів виконується на один виклик вашого ендпоінта; для сценарію вашого варіанта (розділ «20 варіантів завдання») це має показати проблему N+1.

`DB::listen()` у [`ProfilePostListing.php`](../../project8-9/blog/app/Http/Middleware/ProfilePostListing.php) зафіксував **4 SQL-запити** на автентифіковане завантаження сторінки з 15 статтями: підрахунок для пагінації, статті, автори й теги. Наявне eager loading `with(['user', 'tags'])` у [`PostController.php`](../../project8-9/blog/app/Http/Controllers/PostController.php) збережено. Окремий сценарій [`lab7_scenarios.php`](../../project8-9/blog/scripts/lab7_scenarios.php) показав 15 запитів підрахунку для 15 статей; цей навмисно повільний цикл не входить до API. Сценарій тепер лише читає дані: він вимагає `APP_ENV=local` або `testing`, SQLite-файл у тимчасовому каталозі, `CACHE_STORE=array` і точний збіг `LAB7_BENCH_DB_PATH` зі шляхом підключення. Якщо статей немає, виконання припиняється без створення записів.

### Крок 4. Додати індекс на стовпець фільтрації вашого домену.

> Виконайте EXPLAIN для запиту з фільтром вашого варіанта до створення індексу, створіть CREATE INDEX ... на потрібний стовпець, повторіть EXPLAIN і порівняйте type/rows до і після.

Автор у схемі — `posts.user_id`. Для `SELECT * FROM posts WHERE user_id = 1` команда `EXPLAIN QUERY PLAN` у локальній SQLite до міграції повернула `SCAN posts`, після — `SEARCH posts USING INDEX posts_user_id_lab7_idx (user_id=?)`. `PRAGMA index_list('posts')` до міграції повернув порожній список. Міграція [`2026_11_10_000000_index_posts_user_id.php`](../../project8-9/blog/database/migrations/2026_11_10_000000_index_posts_user_id.php) спершу перевіряє наявні індекси: якщо індекс із першим стовпцем `user_id` уже існує (типово для MySQL FK), дубль не створюється. SQLite-план не має полів MySQL `type/rows`; наведено його фактичний `detail`.

### Крок 5. Усунути N+1-запит.

> Перепишіть сценарій вашого варіанта так, щоб замість запиту в циклі виконувався один запит (GROUP BY, JOIN або одне агрегатне SELECT) - переконайтеся лічильником із кроку 3, що кількість запитів справді зменшилася.

Ізольований сценарій замінює 15 викликів `SELECT COUNT(*) FROM posts WHERE user_id = ? AND deleted_at IS NULL` одним запитом `SELECT user_id, COUNT(*) AS cnt FROM posts WHERE deleted_at IS NULL AND user_id IN (1) GROUP BY user_id`. Лічильник показав **15 → 1** запит; результат для автора — `100` статей. Час окремого виконання: `0.747 → 0.629 мс` до індексу та `1.222 → 0.410 мс` після індексу. Ці мікровиміри не є порівнянням HTTP-пропускної здатності.

### Крок 6. Додати кешування «важкого» запиту вашого варіанта.

> Реалізуйте файловий кеш або APCu для агрегатного/спискового запиту вашого домену з розумним TTL (наприклад, 30–60 секунд); переконайтеся, що після зміни даних (додавання/редагування запису) кеш або інвалідується явно, або природно застаріває за TTL, а не показує назавжди застарілі дані.

Метод `listRecent($limit)` у [`PostService.php`](../../project8-9/blog/app/Services/PostService.php) кешує останні статті на **45 секунд** через Laravel Cache (у локальному тесті — файловий драйвер). Новий захищений маршрут `GET /api/posts/recent?limit=10` у [`api.php`](../../project8-9/blog/routes/api.php) повертає `PostResource` зі зв'язками автора й тегів. Після успішного коміту створення, редагування або видалення змінюється один ключ версії кешу; усі значення `limit` відразу переходять на новий простір ключів. Старі записи зникають за TTL. Це працює з database cache store й не робить 100 операцій видалення на запис. Початковий вимір із файловим кешем до цієї зміни: холодний виклик — 3 SQL-запити, `8.653 мс`; теплий — 0 SQL-запитів, `0.581 мс`. Новий ізольований запуск з `CACHE_STORE=array`: холодний — 3 запити, `9.107 мс`; теплий — 0 запитів, `0.149 мс`. Це різні умови кешування, їх не слід порівнювати як приріст продуктивності. Регресійний тест перевіряє database cache store, інвалідацію після всіх трьох операцій та відсутність інвалідації після rollback.

### Крок 7. Повторно виміряти показники з кроків 1–2 після оптимізацій.

> Виконайте той самий профайлінг і той самий ab-тест на оптимізованому коді; зафіксуйте нові значення часу, пам'яті, Requests per second.

Після відновлення індексу в тій самій локальній БД повторено `ab -n 200 -c 20 'http://127.0.0.1:8797/api/posts'`: `175.97` запитів/с, `113.654 мс` на запит, `0` невдалих. Повторний запис профайлера: `2.529 мс`, `2 097 152 байти`, `4` SQL-запити, статус `200`. Одиничні показники часу й пам'яті отримано з різних, не контрольованих щодо прогріву PHP-процесу запитів; їх не можна вважати ефектом індексу. Кеш `listRecent()` не застосовується до звичайного пагінованого `/api/posts`, тому його виграш не приписується цій HTTP-серії.

### Крок 8. Оформити короткий звіт «до / після».

> У README чи коментарі на початку скрипта зведіть у таблицю чи список: час виконання, кількість SQL-запитів, Requests per second - до оптимізацій і після; додайте одне речення пояснення причини різниці.

| Показник | До (без індексу) | Після (з індексом) |
|---|---:|---:|
| Один HTTP-запит, мс (неконтрольований прогрів) | 33.858 | 2.529 |
| Пікова пам'ять, байти (неконтрольований прогрів) | 10 485 760 | 2 097 152 |
| SQL-запитів на `/api/posts` | 4 | 4 |
| Запитів/с, `ab -n 200 -c 20` | 174.91 | 175.97 |
| Час/запит, мс | 114.347 | 113.654 |
| Невдалих запитів | 0 | 0 |
| Підрахунок статей автора, SQL-запитів | 15 | 1 |

Індекс покращує план окремого пошуку за `user_id`, а `GROUP BY` прибирає повторні підрахунки тільки в ізольованому сценарії. Звичайний `/api/posts` уже використовував eager loading, не фільтрує за автором і не використовує кеш `listRecent()`. Тому виміряні зміни часу, пам'яті та пропускної здатності `/api/posts` не доводять ефекту цих оптимізацій; розкид і прогрів процесу могли вплинути на результати. Початкові перевірки Lab 7: `php artisan test` — 20 тестів, 87 тверджень; після виправлень — 21 тест, 100 тверджень. `npm test` — 18 тестів; `npm run build` — успішно. Загальний `vendor/bin/pint --test` повідомив про 48 файлів зі стильовими відхиленнями, зокрема старий код; змінені нові файли відформатовано окремо. Скріншотів немає. Перед розгортанням міграцію треба окремо переглянути й застосувати вручну до потрібної БД; тут вона виконувалась тільки на `/tmp/lab7-blog.sqlite`.
